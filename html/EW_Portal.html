Overview of the codebase

Neutron is EpicWorld's single source of truth for location-based data. It brings in datasets about places (schools, hospitals, ATMs, census and RBI indicators and more), cleans and enriches them, ties every record to a geography, and lets analysts explore the result through reports, region views and plain-English questions answered by AI.

Scope of this review: the dia-neutron-service repo, using branch dev-backend (backend, last commit 2 Nov 2026) and dev_frontend (frontend, last commit 27 Oct 2026). The ei-etl repo is out of scope for now.

Product Requirements – Neutron as built today

What the product does today, in plain language, based on the dev-backend and dev_frontend code. Each feature is labelled Live, Partial / Optional or Planned / Broken.

1. Vision

Give EpicWorld one trusted, quality-checked home for every dataset about places. Anyone in the business should be able to explore it by geography, combine it in reports and ask questions in plain English, without writing SQL.

2. Problems it solves

  • The same information sits in many places (government lists, map listings, financial indicators) with different formats, duplicates and gaps.
  • Data is only useful for location decisions once every record is tied to a known place: state, district, sub-district, village or pincode.
  • Analysts lose time writing SQL and stitching files together by hand.
  • Leaders need one version of the truth, with a history of what changed.

3. Who uses it

Data Steward

Uploads and maps datasets, watches processing, adds rows and retires versions.

Business Analyst

Builds reports, filters master data, asks questions and downloads results.

Regional Analyst

Explores data by geography, compares areas and lists places within them.

Platform Admin

Keeps the pipelines healthy, refreshes region views and handles deployments.

4. Features

A. Access & home

Sign-in & permissions

Live

Users sign in with their EpicWorld (Enmasse) account and stay signed in while active. Two sensitive actions, adding rows to a finished version and deleting a version, are limited to a minimum role (admin by default). Everything else is open to any signed-in user.

Dashboard

Live
  • Totals for datasets, data points and places (POIs), plus geography coverage
  • Every dataset version's processing stage and % complete
  • Play / pause for each version

B. Bringing data in

Dataset catalogue (POI & Non-POI)

Live

Separate lists for place data (POI) and area/indicator data (Non-POI), with search, filters, resume-a-draft and list download.

Guided upload wizard

Live
  1. Source: upload a CSV, or connect to a BigQuery table and test the connection.
  2. Dataset details: new dataset or a new version of an existing one, publisher, licence, update frequency and keywords.
  3. Column mapping: match file columns to required fields (POI needs latitude, longitude, name, address, category and a unique ID).
  4. Review: row counts, missing values and duplicate-ID warnings, then submit or save as a draft. For Non-POI, users can choose to skip gap-filling.

Versions

Live

Each upload of an existing dataset becomes a new version with its own status and history. For POI data, one version is the primary source of locations.

C. Automatic quality processing (after every import)

Find duplicates across sources (POI)

Live

New places are compared with existing places in the same category and nearby. For prepared categories, AI (Gemini) decides whether two records are the same place; for others, name similarity does. Matches share an entity ID.

Attach geography (POI)

Live

Each place is assigned its state, district and so on down to the lowest geographic unit, plus an address. A place shows up in previews, reports, regions and the dashboard only once this step finishes.

Fill missing numbers (Non-POI)

Live

Missing numeric values are estimated with one of three statistical methods, each with a confidence score, and the estimated cells are flagged. Users can opt out per upload. This can't be triggered from the dashboard: that button is Broken because the frontend and backend disagree on the endpoint.

Roll up to higher levels & map files (Non-POI)

Live

Values are aggregated from lower to higher geographic levels using catchment overlaps, and GeoJSON / GeoPackage files are produced for mapping tools.

Copy to BigQuery

Optional

When configured, finished versions are copied to BigQuery for wider analytics.

Daily geography refresh

Live

Every night at 23:59 IST, changes to the geographic hierarchies are synced into Neutron.

D. Looking after datasets

Dataset detail & preview

Live

Browse records with column filters (text, number and multi-value categories), geography and category filters. Download as CSV, Excel, a summary report, GeoJSON or GeoPackage, with filters applied.

Add more rows to a finished version

Live
  • POI: new rows are appended, de-duplicated and geo-tagged, and appear only when complete.
  • Non-POI: matching rows are overwritten, then gap-filling, roll-up and export re-run.
  • If an update fails, it rolls back automatically.
  • Each update is kept in the version's update history, and an email/Slack message reports success, failure or rejection.

Delete a version (with undo)

Live

An impact preview first shows which reports will be archived and which views will refresh. Deletion is then scheduled with a 24-hour undo window, after which data is removed from Postgres and BigQuery and only an audit record remains.

E. Using the data

Reports workspace

Live

Create a market report (Non-POI) or a POI report, add datasets of one type, and work with a combined table: filter, sort, paginate, save the view and download.

Ask questions in plain English (Reports)

Live

Type a question and the AI writes and runs the query, shows the table and can add a short written analysis. Off-topic questions are politely declined. Each question stands alone, with no chat memory.

Dataset discovery assistant

Live

Describe what you need (for example, "hospital beds by district") and get a ranked list of matching datasets.

Regions explorer

Live

Pick a geographic hierarchy and see key areas, data points and the places in each unit. Change levels, search and download CSVs.

Region chatbot

Live

Ask questions about the region on screen. The bot asks for clarification when a question is ambiguous, answers with text and tables, and offers a CSV for large results.

Geographical viewer

Live

A menu link opens the separate map application (geo.neutron.epicworld.com).

5. Key business rules

Every record must have a unique ID; a new version must use the same ID scheme.
Reports contain either POI or Non-POI datasets, never both.
Choosing several categories in the UI means all of them (AND). In the chatbot, it means any (OR) unless the user says “and”.
Region views refresh manually, not after every upload. A refresh is blocked while a version is being updated.
Only one add-rows update can run on a version at a time. Region and report refreshes for that version wait until it finishes.
Deletion is blocked while any version of the same dataset is still processing.

6. Not in this release

  • Restoring a deleted or earlier version
  • Chat that remembers earlier questions
  • Notifications on first upload (only add-rows sends them)
  • Different access per persona beyond the two gated actions
  • Re-running enrichment or gap-filling from the UI
  • Automatic region-view refresh
  • BigQuery Insights; a searchable knowledge base (RAG) for metadata
  • Text, image or video data

Architecture observations
  • Everything runs on one VM, and the compose file isn't version-controlled, so the environment can't be rebuilt from the repo.
  • Postgres serves transactional work, heavy rollups, materialized-view rebuilds and AI-generated queries, all on the same instance.
  • Beat runs inside the worker, so adding worker replicas would duplicate the scheduled jobs.

Prospective roadmap

A phased plan for taking over and modernising Neutron. First we take control safely and make production robust, then close the product gaps, then re-architect for scale. Durations are indicative for a team of about 4–5 engineers (3 backend/data, 1 frontend, 1 DevOps) and should be re-planned after Phase 0.

Phase 0Weeks 1–4 · Take over & stabilise
  • Knowledge transfer with the vendor; validate the in-repo wiki against the code and production
  • Access and inventory: VMs, the off-repo compose file and deploy.sh, all .env secrets, GCP/BigQuery, Gemini keys, Enmasse, Catchment DB
  • Bring the VM compose and deploy scripts into git; agree one branching model (trunk-based, frontend and backend together)
  • Fix critical items: the DEBUG tuple bug, the global access token, committed DB passwords (rotate), a read-only DB role for AI SQL
  • A CI gate on every PR: ruff, eslint, pytest, vitest, secret scan, dependency audit
  • Back up production and test a restore
Outcome: we can build, test, deploy and recover the system ourselves
Phase 1Weeks 5–12 · Production hardening
  • gunicorn plus a reverse proxy; separate beat; per-stage Celery queues
  • Upgrade Django 4.2 → 5.2 LTS (4.2 support ended April 2026)
  • Move to managed services: Cloud SQL, Memorystore, and GCS for uploads and exports
  • Secret Manager; one settings module per environment
  • Observability: JSON logs, metrics, alerts, readiness probes, runbooks
  • Run the vendor's producer/consumer load-test plan and set a baseline
Outcome: secure, observable, scalable production with known capacity
Phase 2Weeks 13–20 · Close product gaps
  • Fix the imputation trigger from the dashboard; re-run enrichment and gap-filling from the UI
  • Automatic, incremental region and report view refresh after processing
  • Proper role-based access per persona; audit log
  • Notifications for all key events (upload complete, failure, deletion)
  • Restore a version within a retention window
  • Multi-turn chat with saved history (Reports and Regions)
Outcome: v1.0 commitments fulfilled; fewer manual admin tasks
Phase 3Weeks 21–32 · Re-architect for scale
  • Break up oversized modules (8k-line upload handler, 3k-line pages) into service layers
  • Read replica or BigQuery as the analytics tier; CDC instead of bulk push
  • Event-driven pipeline stages with retry and dead-letter handling
  • A separate AI module: prompt versioning, LangSmith evaluation in CI, cost dashboards, model routing (Flash vs Pro)
  • Infrastructure as code (Terraform) and blue/green deploys
Outcome: a platform that scales with data volume and team size
Phase 4Week 33+ · Neutron 2.0
  • A searchable knowledge base (RAG) over the dataset catalogue for discovery
  • BigQuery Insights and self-service analytics
  • Public/partner APIs and data products for Epic Intelligence and clients
  • Text and document ingestion, if the business needs it
Outcome: Neutron becomes a self-service data product
