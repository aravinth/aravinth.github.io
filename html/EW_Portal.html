Overview of the codebase

EpicWorld helps businesses and investors understand places. It puts data such as shops, schools, weather and population onto maps at different geographic levels (state, district, village, pincode, hex). The workspace has two repositories, and each owns one half of that journey.

Repo 1

dia-neutron-service

“Neutron” – the data lake / data-onboarding tool

Brings raw datasets in from a CSV file or a BigQuery table, describes them, tidies the columns, ties records to locations, fills gaps and stores the result. Data operators use it.

FrontendReact 19, Vite, TypeScript, Tailwind, Radix UI, React Query, Zustand

Key concepts

Layer

One property shown on a map, such as temperature, number of schools or footfall. It has values at one or more geographic levels.

POI vs Non-POI

POI (point of interest) has an exact latitude/longitude, such as a shop or a hospital. Non-POI belongs to an area, such as a village or a district.

Geo hierarchy

Country → State → District → Sub-district, plus independent levels: pincode, village, H3 hex. Neutron reads the hierarchies from a separate catchment_db.

Product Requirements – as built today

This describes what the product does today, based on the current code, in plain language. Each feature is labelled Live, Partial or Planned.

1. Vision

Give EpicWorld one trusted place where any location-based dataset is brought in, cleaned and tied to geography. That dataset can then be turned into map layers that clients use to judge markets, sites and investments.

2. Who uses it

Data Operator

An internal team member who finds datasets, uploads them, describes them and keeps them current. Main user of Neutron.

EpicWorld Client / Analyst

Views map layers in Epic Intelligence. In the future, will pick datasets and turn them into their own layers.

Admin

Manages users and roles (super admin → read-only) and watches overall data health on the dashboard.

3. Problems it solves

  • Datasets arrive in many shapes (spreadsheets, cloud tables) with inconsistent columns and missing values.
  • Data is only useful on a map once it is tied to a known geographic unit (state, district, village, pincode, hex).
  • Teams need to know where each dataset came from, its licence, how often it updates and whether it's client-confidential.
  • Clients need a fast, uniform way to see any dataset as a map layer.

4. Features

4.1 Secure sign-in & roles

Live

Users sign in with their company (Enmasse) account. The session renews itself quietly while they work and sends them back to the login page when it expires. Seven role levels exist: super admin, admin, manager, supervisor, user, guest and read-only.

4.2 Home dashboard

Partial
  • Data overview: how many data sources and data points are active, completed or pending.
  • Process progress: % complete for geo-tagging, enrichment and gap-filling. The geo-tagging and enrichment steps don't run yet, so they stay at 0.
  • System health: server CPU and memory use.
  • Top POI categories: currently shows placeholder numbers.

4.3 Add a new dataset (guided 4-step wizard)

Live
  1. Basic info: name, keywords, type (POI or Non-POI), and whether it's private client data (with the client name).
  2. Source details: publisher, source link, level of detail (granularity), update frequency, licence and description.
  3. Column setup: pick each column from the file, rename it, describe it, drop the ones you don't need, and mark latitude/longitude for POI data.
  4. Review & import: check everything, then start the import.

Data can come from a CSV upload or a BigQuery connection. For BigQuery, the user uploads a service-account key, tests the connection and picks a table.

4.4 Save as draft & resume

Live

Work can be saved part-way and picked up later. Right after upload, the system counts rows and missing values per column in the background, so the user sees data quality before importing.

4.5 Import & versioning

Live

The import runs in the background. Every upload creates a new version of the dataset, so history is kept. Statuses: draft → import started → import completed / failed. POI records keep their map point.

4.6 Merge new data into an existing dataset

Live

Add a fresh batch to a dataset that already exists. The wizard pre-fills details from the latest completed version and lets the user choose the geographic hierarchy and level. Missing values are flagged to be filled during the merge.

4.7 Dataset catalogue & details

Live

Browse POI datasets with search, filters, sorting and pagination. Open a dataset to see its versions, record counts and processing status. The Non-POI catalogue is a placeholder for now.

4.8 Fill missing values (imputation)

Partial

Can estimate missing numbers with two statistical methods (KNN and MICE) and record which values were estimated. Today it can only be triggered through the API, not from the screen, and large datasets may time out.

4.9 Download

Partial

Download any dataset version as CSV or Excel, plus a summary report. The download button on the POI list isn't connected yet.

4.10 Geo-tagging & enrichment

Planned

Automatically attach each record to its state, district, village, pincode and hex, then enrich it with extra attributes. Placeholders for status and progress tracking exist, but the processing isn't built.

4.11 Map layers for clients (N-Layer)

Prototype
  1. Neutron announces that a new dataset is ready.
  2. A client browses available datasets and picks one.
  3. They choose POI or Non-POI (POI only if location points exist) and the column to show as the value. For example, a weather dataset can become separate temperature, rainfall and humidity layers.
  4. The system builds the layer in the background and shows progress until it is ready on the map.

Today only the data-copy engine exists, for POI data. The client-facing screens, the layer catalogue and the progress tracking are designed but not built.

4.12 Reports, assistant chatbot, Geographical app link

Planned

The Reports menu shows a placeholder, and the chatbot widget exists but is switched off. The “Geographical” menu item opens a separate existing application in a new tab.

5. Rules the product follows

  • A POI dataset must include latitude and longitude, plus a few other required fields, before it can be imported.
  • Dropped columns are never imported, and renamed columns keep their new names everywhere afterwards.
  • Uploaded source files are deleted once the import succeeds.
  • Client-private datasets are flagged so access can be limited to that client.

6. Not in scope today

  • Scheduled or automatic refresh of datasets
  • Deleting layers or datasets from the UI
  • Previewing a layer before it is built
  • Self-service for external clients inside Neutron

What changes in the target

  • One gateway (Nginx / API Gateway) with TLS and SSO in front of every UI and API.
  • Stateless app tier: uploads go to GCS through signed URLs, secrets come from Secret Manager, and Redis/Postgres are managed services. The API and workers can then scale out.
  • A complete Neutron pipeline: import → geo-tag → enrich → impute, all as background jobs, ending with a publish step that writes curated tables to Neutron BigQuery. This removes the hidden external sync.
  • Event-driven layer creation: a dataset-ready event registers the dataset in neutron_datasets. The client creates a layer, which is stored in layer_metadata, and that launches Dataflow. Job status flows back to the Layer API.
  • Generic layer_data table in ClickHouse (MergeTree, partitioned by month, ordered by layer and district) serving all POI and Non-POI layers.
  • Cross-cutting: Secret Manager · Cloud Logging / Monitoring and alerts · CI/CD (Cloud Build or GitHub Actions) · infrastructure as code (Terraform).

  • The region, analysis and postupload_processor apps are empty.

ei-etl: BigQuery → ClickHouse layer ingestion

An Apache Beam pipeline packaged as a Dataflow Flex Template. A JSON mapping config defines the source table, target table and per-column transforms. Each run generates one layer_id.

Gaps seen in code
  • The Django → Celery → Dataflow trigger exists only in django_trigger_example.py. It isn't wired into the EI app.
  • The layer_metadata and neutron_datasets tables from the design doc aren't implemented, and nothing writes job status back.
  • Only the POI mapping (poi_layer_data) is ready. The Non-POI mapping is a sample.

Prospective roadmap

An indicative, phased plan that first makes the current system safe, then finishes the Neutron pipeline, then delivers N-Layer end to end. Durations assume a small team (2–3 backend, 1 frontend, 1 DevOps/data engineer) and should be re-estimated after Phase 0.

Phase 0Weeks 1–3

Stabilise & secure

  • Fix critical security items: hard-coded secret key, the DEBUG flag that is always on, the shared global token, open ALLOWED_HOSTS
  • Commit Django migrations so the database schema can be reproduced
  • Fix the Docker image (Python 3.8 vs the 3.11 the project targets) and add Redis, Celery, frontend and gunicorn to compose
  • CI: lint (ruff, eslint), the existing unit tests, container build
  • Move secrets to Secret Manager
Outcome: a deployable, secure baseline
Phase 1Weeks 4–9

Complete the Neutron core

  • Geo-tagging (geobound) job: point-in-polygon against catchment hierarchies (state → hex)
  • Enrichment (augmentation) job
  • Move imputation to Celery, with a UI trigger and progress display
  • Publish step to Neutron BigQuery (curated POI / Non-POI tables)
  • Non-POI catalogue, POI list download, real dashboard numbers
  • Move uploads to GCS
Outcome: raw file → curated, geo-tagged dataset in BigQuery, without manual steps
Phase 2Weeks 10–16

N-Layer MVP

  • neutron_datasets and layer_metadata tables plus APIs (notify, list, create layer, status)
  • Generate the mapping config automatically from the client’s choices
  • Celery → Dataflow launch, with job status written back
  • Generic ClickHouse layer_data schema; Non-POI mapping
  • Layer-creation screens and status page for clients
Outcome: a client creates a layer from any Neutron dataset and sees it on the map
Phase 3Weeks 17–22

Scale & operate

  • Incremental sync / change data capture, and scheduled refreshes
  • Data quality checks: row counts, nulls, outliers, geo coverage
  • Idempotent loads (no duplicates when a load is re-run); layer delete and re-run
  • Monitoring, alerts, dashboards; Terraform for all infrastructure
  • ClickHouse materialized views for common map queries
Outcome: reliable, observable, self-refreshing layers
Phase 4Week 23+

Product expansion

  • Layer preview before the full build
  • Reports module
  • Assistant chatbot over the dataset catalogue
  • Custom transforms; client self-service onboarding
  • Retire the legacy Django templates / static UI
Outcome: self-service geospatial data product
